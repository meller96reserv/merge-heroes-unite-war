# TASK-0043 — Native lifecycle fixture

Run ten complete RN → Cocos → RN cycles and ten Home → foreground cycles on each native target. A UI-driver exit code is insufficient: correlate native owner logs, Cocos hide/show/tap/frame counters, fresh session handshakes (Android) and fresh retained-session ping responses (iOS). Preserve failed attempts separately. Compare pre/post background frame/time counters and require zero applied catch-up on the first resumed presentation frame.

Android retains RN and destroys the Cocos Activity/engine on each dismissal. Its epoch guard rejects delivery queued for a destroyed owner. iOS retains one paused engine and callback; UIKit active/inactive notifications forward to the existing Cocos platform lifecycle exactly once per transition while Cocos is visible. Returning to RN pauses Cocos. No native loop starts while RN alone is visible. Host JS cancels queued old-owner messages on reset/close.

The fixture excludes gameplay, rewards and durable saves. Presentation skips the first resumed delta and records both raw and applied values; this does not define economic offline time. Audio focus, memory slope and process-death/save handshake remain separate acceptance cases. Real device results remain NOT_RUN unless executed.

The iOS flow uses [Maestro launchApp](https://docs.maestro.dev/api-reference/commands/launchapp) with `stopApp: false` to foreground the existing process; the default would restart it and invalidate the background test. Native PID/session logs must confirm survival. Empty permissions avoid requesting new app permissions. Source inspection found no UIApplication lifecycle forwarding in the initial RN delegate, so the owned Cocos runtime now subscribes to UIKit notifications once.

The first Android background test failed with zero completed cycles: the RN template MainActivity used singleTask, so a launcher intent cleared the Cocos Activity above it. The fixture changes MainActivity to singleTop and reruns both ten-cycle series. Previous failure evidence remains in evidence/lifecycle-android-background.json and logs/lifecycle-android-background-events.log.

Further diagnosis: the second attempt kept Cocos but put a duplicate RN Activity above it because the cold-start component-only intent differed from the launcher intent. Cold start and foreground with matching MAIN/LAUNCHER intents pass ten cycles. Use `adb -s emulator-5556 shell am start -W -a android.intent.action.MAIN -c android.intent.category.LAUNCHER -n com.kiselnativeprobe/.MainActivity -f 0x10200000`. Mixed entry intents are an explicit TASK-0046 routing follow-up. This bounded result does not approve that failing route.
