# React Native and Cocos integration

Status: [PROPOSED strategy A; NOT VERIFIED]. Compare A: full-screen native Cocos Activity/ViewController launched from RN; B: embedded Cocos surface as RN native view; C: Cocos web build in RN WebView. A is preferred for a clear engine/lifecycle owner and native rendering. B adds surface sizing, touch arbitration, render-context ownership and simultaneous RN composition risks. C can provide a fallback preview but changes performance/audio/storage behavior and cannot be silently substituted for the native requirement.

Android and iOS must share the versioned bridge contract but may use different host glue. Current RN documentation describes TurboModules/codegen for new native integrations; current Cocos 3.8 documentation exposes Java/Objective-C reflection and script callbacks. These primitives do not prove that a supported RN+Cocos integration exists. The spike must prove the assembled product on installed versions.

At planning completion Cocos and native projects were absent. During implementation TASK-0037…0039 installed the pinned toolchain and verified standalone Cocos3.8.8/RN0.86.3 builds on Android API36 and iOS26.2 simulators, including actual scene rendering and touch. See the [toolchain lock](../../spikes/rn-cocos/toolchain.json), [Cocos evidence](../../spikes/rn-cocos/cocos-probe/README.md) and [RN evidence](../../spikes/rn-cocos/rn-probe/README.md). Integrated host/protocol/lifecycle and physical-device acceptance remains separate and unpassed. Full production host work depends on TASK-0046.

Spike scope is a colored Cocos scene, tap counter, bidirectional ping, lifecycle/audio probe and repeated enter/exit. No game features. Run 10+ reopen cycles, rotate/background/foreground, Android Back, iOS dismissal, process death and invalid/stale message cases. Capture build commands/logs, device IDs (redacted for sharing), memory traces and screen recordings.

TASK-0040/0041 now prove bounded native host entry/touch/return on [Android API36](../../spikes/rn-cocos/android-host-results.md) and [iOS26.2 Simulator](../../spikes/rn-cocos/ios-host-results.md). Android destroys its Activity/engine on exit; iOS retains one paused engine and switches the RN-owned window root to satisfy the engine's native view lookup. The full strategy remains unverified until bridge/lifecycle/audio/memory/physical acceptance passes. These platform-specific lifetimes must preserve the same logical session contract in TASK-0042/0043.

Failure path: repair lifecycle/ownership once with a bounded issue list; if native A cannot pass, record ADR evidence and compare B, then C, with explicit fidelity/performance tradeoffs. Flutter is only a separately approved architecture change after evidence, never an automatic implementation detour.

Primary sources: [RN native platform](https://reactnative.dev/docs/native-platform), [Turbo native modules](https://reactnative.dev/docs/turbo-native-modules-introduction), [Cocos Java reflection](https://docs.cocos.com/creator/3.8/manual/en/advanced-topics/java-reflection.html), [Cocos Objective-C reflection](https://docs.cocos.com/creator/3.8/manual/en/advanced-topics/oc-reflection.html).

## Traceability

TASK-0042 [bounded native bridge](../../spikes/rn-cocos/bridge-results.json) passes on both simulator targets: shared typed receiver, exact invalid/stale code/path rejection, native UTF-8 cap and one color application despite duplicate/conflicting requests. On iOS, the host must own a copied JsbBridge callback because the pinned non-ARC vendor setter only assigns it. Browser uses the same receiver through a development-only transport. Lifecycle/audio/memory/physical acceptance remains open.
