# SEC-001 — exposed proxy authentication in historical diagnostics

Classification: REAL / POTENTIALLY REUSABLE. The detected Base64 Basic value decodes to proxy authentication and exactly matches the ambient HTTP_PROXY and HTTPS_PROXY credentials. A public proxy host is involved; this is not a loopback fixture. No credential value, decoded user/password, or credential hash is included in this report. No authentication attempt using the exposed value was made.

Four raw spike logs contained the value: audio-web-export-console.log, bridge-web-export.log, cocos-preview-console.log, lifecycle-web-export.log under spikes/rn-cocos/logs. All four paths were removed from branch history with git-filter-repo 2.47.0 using system Git2.50.1. The original alert commit18cad48 was not the earliest affected commit; the history rewrite includes earlier occurrences. An auxiliary Codex tree snapshot was also sanitized without removing its other files. Current local copies of the four logs were redacted and remain ignored.

The isolated and adopted local repositories pass an exact-value scan over every reachable ref: 1,933 blob objects, zero matches. Existing dirty tracked files were fingerprinted and verified unchanged during ref adoption; new battle components were never reset, stashed or removed. Old affected branch/HEAD reflogs were expired. Unrelated refs were preserved. The same clean commit graph is force-pushed with an explicit expected-old-SHA lease; remote verification is recorded separately. No main-branch rewrite or mirror push is used.

Rotation status: OWNER_ACTION_REQUIRED. The credential belongs to externally configured proxy infrastructure. This workspace exposes use of the proxy but no provider account, rotation API or administrative access. Changing local environment variables would not revoke the leaked credential. The proxy owner must rotate/revoke it outside this repository. Do not classify this incident as fully closed before rotation is confirmed.

GitHub cached commits/PR refs and other people's clones cannot be proven erased by a branch force-push. See [GitHub removal guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository). If cached access requires removal, the repository owner must request GitHub Support cleanup. No support message was sent. Other clones must use the cleaned history and must not merge old history back.

Prevention: raw runtime logs and spike log directories are ignored; the installed versioned pre-commit hook scans only staged content and prints rule/path, never matches. It rejects raw logs, authorization values, URL userinfo and private keys. `python3 tooling/security/sanitize-log.py INPUT OUTPUT.json` creates an allowlisted diagnostic summary without copying free-form messages or request objects. Commit reviewed acceptance evidence, not network/console dumps. Synthetic regression tests verify the scanner and sanitizer. New clones enable the hook with `git config core.hooksPath .githooks`.

This incident does not retroactively change native-spike PASS/PARTIAL results. Any historical raw-log hash/path now describes retired evidence; retained structured probe reports remain the acceptance source. Production remains RN/TypeScript/Expo/Skia.
